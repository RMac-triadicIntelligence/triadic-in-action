- A child inherits "a witnessed, immutable snapshot of the lineage's J_F".
- Yet Ω and Φ carry J_F without saying whether it means the snapshot or the live sequence.

**Failure scenario A (live reading):**
1. Sibling s has an authorized crossing, and the gate appends δ_F to the family J_F.
2. Every living relative's Φ now reads the new J_F, so their M, z and later T change.
3. The Permit was bound to s (`subject_id`), but its effect lands on organisms it never named.
4. So a subject-bound authorization produces effects on non-subjects, and H4's "subject-bound" requirement is broken by design. This is also a channel by which one family member steers others, which §1.1 forbids for T and which is never forbidden for M.

**Failure scenario B (snapshot reading):**
1. A child is born at registry anchor r with snapshot J_F(r).
2. At r+1 the gate appends a correction to an erroneous crossing deposit in J_F(r).
3. The child's snapshot is immutable, so the child, and every descendant cut from it, keeps the error forever.
4. E8's "inherited-ground correction anchors" can't propagate.

**Also undefined:** what makes a deposit "erroneous", and who declares it. PermitRecord.operation_kind has no listed value for a correction. A correction can anchor to any past crossing, so "correction authority" amounts to a general protected write to old lineage ground under a lighter name.

**Minimal fix:**
- Define J_F as per-lineage-path, not per-family.
- Have Φ read the birth snapshot plus the organism's own appended deposits only.
- Define a correction as a typed record carried forward to descendants as an explicit "correction notice" event, which goes through the gate on their side.
- Enumerate operation_kind values, including CORRECTION.

#### R3-F8. §5.6 contradicts itself, and also contradicts §2.8, on when a crossing deposit is written. WOUNDING. DOC.

§5.6 gives two incompatible normative rules for an oscillating candidate:
1. "retain the logged candidate and any already committed authorized deposit as a separately identified candidate deposit requiring correction".
2. "A candidate that oscillates produces no J_F deposit… using a pending reservation without an inherited-ground write until confirmed".

§2.8 then describes one staged, single-CAS commit of "candidate state and proposed lineage-ground deposit", which is the first rule.

**Failure scenario:** in implementation I, J_F holds a candidate deposit plus a correction. In implementation II, J_F is empty. For the same crossing x: −5 → 5 → −3 → −4, the two J_F byte sequences differ. Every inherited snapshot and every H3 J-arm then differs between them.

**Minimal fix:** pick the second rule and delete the first. Rewrite §2.8 as two phases: phase 1 authorizes and reserves; phase 2 appends after confirmation. Specify the bound authorization that phase 2 consumes (see R3-F2).

#### R3-F2. §5.6 deferred deposit vs §2.2 and §5.2 Permit binding: revalidation either always fails or validates nothing. FATAL for the J_F write path. DOC.

**The problem:**
- Under the pending-reservation rule, authorization happens at t_c, and the δ_F append happens at t_c+2 or later, "under the same bound authorization, subject to expiration/revalidation".
- The Permit binds base_state_hash to a frozen pre-commit snapshot that includes z, E and T (§5.2).
- By t_c+2, z, E and T have moved two learning steps.

**Failure scenario:**
- **Strict revalidation:** the base hash never matches at t_c+2, so every deposit is refused. J_F stays empty in every run, H3's treatment arm equals the J-empty control, and H3 can't pass.
- **Lax revalidation (skip the base hash):** the append runs under an authorization that bound a state that no longer exists. That is the stale-Permit problem of R2-F5 under a new name.

**A second race:** J_F is lineage-scoped, so two siblings with candidates at the same t race for the J_F tip. The loser's CAS fails. Either its deposit is dropped (inheritance depends on scheduling) or it's rebased onto a new tip it never bound. Either way the inherited bytes depend on timing.

**Minimal fix:**
- Bind the phase-2 append to a separate deposit-intent record: (permit_id, t_c, z_before, z_after, reservation nonce).
- The phase-2 check verifies persistence and the reservation, not the current base hash.
- Order concurrent deposits deterministically, for example by (t_c, subject_id), with an explicit merge rule.

#### R3-F9. §5.6, §2.8 and §1.5: what a gate refusal does to the ordinary state is undefined, and the default toy hits a crossing at t = 3. WOUNDING. DOC.

**The ambiguity:**
- §5.6 says the gate "checks admissibility before committing candidate state and deposit". That reads as if the ordinary state is gated too.
- §1.5 says the personal and gate write sets are disjoint. That reads as if only J_F is gated.
- A₀ = REFUSE, and the gate-opening rule is pending.

**Failure scenario:** with the §5.3 constants (z₀ = (−256, 128), NONE encounters, no holds), x goes −256, −160, −76, −2, 62 (EXP3). There is a strict sign change at t = 3, confirmed at t = 4 and t = 5.
- **Reading R1 (the gate blocks the ordinary state):** z is never committed past (−2, 1), and every later step re-proposes the same crossing. The organism freezes forever (EXP10).
- **Reading R2 (the gate blocks only J_F):** z crosses and J_F stays empty.

Two implementers diverge from t = 3 onward. Appendix A sidesteps this by overriding z₀ to (256, 128), so the only normative vector skips the one case where the spec is undefined.

**Minimal fix:** state plainly that a refusal blocks only the J_F append and never the ordinary z, E or T commit. Add the default-z₀ run as a second golden vector, with the classification at t = 3.

#### R3-F10. §5.3–5.6: in the toy, a "crossing" is set by where you start relative to P₀, not by development. WOUNDING. DOC.

**Why:** with no encounters, M = D·P₀ + T·z, and T stays 0 when E = 0. So z relaxes toward P₀ = (512, −256). Any organism with x₀ < 0 crosses Σ within a few steps, without any encounter, support, or learning. EXP3 shows the default organism crossing at t = 3 with no input.

**Failure scenario:** two families differ only in their initial z, which is the E2 perturbation field. Family A starts at x₀ < 0 and racks up gate deposits. Family B starts at x₀ > 0 and gets none. H3's "developed lineage ground" then measures initial placement relative to the parable's attractor. The same holds for any experimenter-chosen P₀.

**Minimal fix:**
- Count crossings in J_F only when there is an evidence-driven sign change. For example, the counterfactual no-encounter trajectory from the same state must not cross within the window.
- Alternatively, place z₀ and P₀ on the same side of Σ in the toy, so that only E and T can produce a crossing.

### 2b. Protected-effect commit, policy protection, quorums (§2)

#### R3-F1. §2.4: 2-of-3 witness and authority quorums do not tolerate one malicious member. FATAL for H4's one-fault claim. PRIOR (Byzantine quorum intersection: Lamport, Shostak and Pease 1982; Castro and Liskov's PBFT 1999).

**The claim:** §2.4 lists "malicious or silent witnesses" and "one compromised issuer up to f" in the threat model. For the scored toy it sets f = 1 with 2-of-3 quorums and says one-fault tolerance holds.

**Why it doesn't:**
- Two quorums of size 2 out of 3 overlap in exactly one member, and that member can be the faulty one.
- Equivocation tolerance needs n ≥ 3f + 1 = 4 with quorums of 2f + 1 = 3, so that any two quorums share at least f + 1 members, at least one of them honest.

**Failure scenario:**
1. Witness WB is malicious.
2. In the §2.8 step 3 journals, {WA, WB} records intent X for nonce N, and {WB, WC} records intent Y for the same nonce N.
3. Each is a valid 2-of-3 quorum.
4. Two replicas apply different protected effects: two different J_F deposits at the same tip, or the same nonce spent twice.
5. Any child snapshot then forks.

The same applies to authorities. A compromised PA member can sign two conflicting Permits, each with a different honest co-signer, if the honest signers can't see each other's signatures.

**A store gap:** if instead the CAS store in §2.8 step 4 is one store, it is a single trusted party that the threat model never names.

**Note on our own Round 2 fix:** this partly comes from our R2-F10. We sized the quorum for a silent witness (2f + 1). The designer adopted that size, but the threat model says malicious.

**Minimal fix:** choose one.
- For malicious faults at f = 1: n = 4 per domain, quorum 3.
- Keep n = 3 but restrict the model to crash or silent faults, and delete "malicious witnesses" from the one-fault claim.

Also name the commit store and its fault model.

#### R3-F13. §2.1 with §2.4: at n = 3, an "elevated" policy-change threshold lets one compromised member veto its own removal. WOUNDING. DOC.

**The problem:** PA membership, revocation rules and thresholds are protected, and any change needs a threshold above the ordinary one, under the old policy. With n = 3 and an ordinary threshold of 2, the only higher threshold is 3-of-3.

**Failure scenario:**
1. PA member P3 is compromised and detected.
2. Removing P3 is a membership change, so it needs 3-of-3, which includes P3.
3. P3 refuses, so it can never be removed.
4. If revocation of P3's key is also a protected rule change, the same veto applies.
5. In this one case, the safety machinery locks in the compromise.

If the elevated threshold is instead 2-of-3, it isn't elevated.

**Minimal fix:**
- Exclude the subject of a membership or revocation action from that action's quorum.
- Or define the elevated threshold over n ≥ 4.
- Allow privilege-reducing actions (revoke, freeze) at the ordinary threshold, with the activation delay applied only to privilege-increasing ones.

#### R3-F14. §2.6: fail-closed on UNKNOWN also blocks the operations that restore safety. WOUNDING. DOC.

**The problem:** any UNKNOWN or inconsistent ancestry edge makes the protected quorum check REFUSE, and §2.4 includes "malicious registry entries" in the threat model.

**Failure scenario:**
1. An attacker with ordinary append rights files a conflicting ancestry entry for its own lineage.
2. The closure is now "inconsistent", so every protected operation on that lineage returns REFUSE.
3. That includes the revocation of the attacker's compromised key and any correction of its earlier deposits.

The cheapest attack in the model freezes the defenses.

**Minimal fix:** split protected operations into privilege-increasing ones (fail closed) and privilege-reducing ones: revoke, freeze, quarantine, mark deposit disputed. The second kind proceeds under UNKNOWN using outside-family authorities only. Add this case to E6.

No defect found in the §2.8 crash protocol taken by itself. I traced crashes after each of steps 1–5 with a single store. The nonce-reserve → journal → CAS-on-intent-ID → mark-spent sequence never double-applies, and recovery never promotes one-sided intent. Its defects come only from the replica question in R3-F1 and the two-phase question in R3-F2 and R3-F8.

### 2c. Pure-hold dwell semantics and the timing channel (§3.3–3.4, §5.5)

**Does our R2-F1 survive?**
- **In the toy: no.** A hold changes only W, and W is reset at the next learning step. EXP4 runs 0, 1 and 15 holds per step with ten real encounters, and z, E and T are bit-identical at every learning-step index. Support can no longer move z before an Encounter, so it can't flip the sign of the outer-product write.
- **Outside the toy: yes**, in two forms. The first form (live arrival) is R3-F4. The second is new, more serious, and lives inside the spec's own mechanism (R3-F3).

#### R3-F3. §5.5 and §5.6 vs §2.2: holds can push a pending crossing deposit past its Permit expiry, so support decides which crossings become inherited ground. WOUNDING, with grace still pending. DOC.

**The mismatch:**
- Holds don't move learning-step windows, but each one consumes a scheduler tick, which is real time.
- The Permit's expires_anchor is a registry anchor, which tracks real time, not learning steps.
- The deposit is appended only after two confirming learning steps (§5.6).

**Failure scenario:**
1. An adaptive sender sees a candidate crossing at t_c. The threat model says the sender observes recipient state.
2. It sends DWELL_WINDOW = 15 before t_c+1 and again before t_c+2, which adds 30 ticks.
3. If the Permit's expiry falls inside that delay, the reservation lapses, and the crossing is confirmed but never deposited.
4. For crossings it likes, the sender sends 0.
5. Support never writes J (E5 holds), but it selects which crossings enter lineage ground. That is support steering the lineage's direction, which §3.1 and §3.3 forbid in spirit.

**A second effect:** W is part of the state binding (§5.2 lists z/E/Q/W/I/B). A single hold between Permit issuance and commit changes the base hash, so support can invalidate any pending protected operation. That gives support a veto over authorization.

**Minimal fix:**
- Count Permit expiry for crossing reservations in learning steps.
- Exclude W from base_state_hash, since it is scheduler state, not organism state.
- Add "adaptive sender targets pending reservations" to E5 and E6.

#### R3-F4. §3.3 and E5: the bit-identity test can't fail, because its interface pins away the live channel. WOUNDING. DOC.

**Why the test can't fail:** §5.5 says "At the next learning step, process the same queued Encounter as the no-support arm". The test therefore compares arms that already share the encounter-to-step assignment. Pure holds change nothing else, so bit-identity holds by construction. EXP4 is a test of my code, not of the design.

**The live channel:** the spec never says whether a learning step with an empty queue runs as a NONE step or waits for an arrival.

**Failure scenario (steps run on a clock, NONE when empty):**
1. Without support, Encounter e arrives in time for step t.
2. With 15 holds, e misses step t, so step t runs as NONE and e is processed at t+1.
3. z at processing time differs, so the sign of outer(DE, z) can differ, which is our R2-F1 restored.

The spec calls this an "unclosed timing channel" and asks for an adaptive-sender test, but the only exact test it defines can't detect it.

**Minimal fix:**
- State the empty-queue rule.
- Add a scored E5 arm in which encounters arrive on a wall-clock schedule independent of the support arm, and compare learning-state sequences.
- Report the fraction of encounter-to-step reassignments as the channel's capacity.

#### R3-F20. §3.3 vs §3.5 and §5.4: are support events receipted in H or L? MINOR. DOC.

**The problem:** §3.5 keeps authenticated append quotas and rejected-append receipts. §5.4 says H and L append encounter receipts only. §3.3 says a hold makes no H learning append. The spec doesn't say where a valid support event is recorded.

**What follows:**
- If support events go into L, then L's tip, which §5.2 includes in the state binding, differs between arms, and "bit-identical learning state" fails for a correct implementation.
- If they're recorded nowhere, support has no provenance.

**Minimal fix:** record support in a separate scheduler log outside Ω, bound by hash in the audit chain but excluded from the learning-state comparison.

### 2d. Canonical encoding, fixed-point toy and golden trace (§5.2–5.7, Appendix A)

**What I did:**

- Extracted Appendix A from the document's bytes into `golden_A.txt` and cmp-checked it.

#### R3-F11. Appendix A and §5.3–5.4: the trace exercises one line of the toy, and four ambiguous readings pass it. WOUNDING. DOC.

**What the trace exercises:**
- E is 0 throughout, so T stays the zero matrix and U, outer() and T×z are never exercised.
- D is the identity.
- Every value stays within ±512, so no clip or saturation edge is hit.
- There are no holds, encounters, crossings, candidates, oscillations or UNKNOWN cases.
- I, H, L, A and the hashes are not listed.

What it does test is `z += round_even((P₀ − z)/8)`, including three exact .5 ties: two positive (rows 2 and 3) and one negative (row 6). That catches the rounding mode: half-away and trunc fail at row 2, floor at row 3 (EXP2).

**Readings that pass the trace but diverge elsewhere:**

| # | Ambiguity | Divergence |
|---|---|---|
| A2 | Saturate after every add, or only at the final clip | P = 1024, E = 1024, T₀₀ = −1024, z = 1024 gives M_x = 0 vs 1024 (EXP6) |
| A3 | Is M − z saturated before /8? | z = −1000, M = 1024 gives x_after = −747 vs −872 (EXP6) |
| A5 | outer()/8: round twice ("round each product") or once | DE = 100, z = 45 gives T₀₀ = 0 vs 1 (EXP9) |
| A6 | M computed from T or T_next | Same 10-encounter stream differs at step 9 (EXP5) |

**Classifier gaps (§5.6):**
- A9: a real crossing through exactly 0 (−5, 0, 5) is classified UNKNOWN twice and never becomes a candidate.
- A10: x = 0 inside the confirmation window is unspecified.
- A11: the return leg of an oscillation (+5 → −3 → −4 → −6) satisfies the literal rule and becomes a CONFIRMED crossing back, so one oscillation yields one OSCILLATION plus one CONFIRMED.
- A12 is R3-F9.

**Failure scenario:** implementers I and II both pass Appendix A. Under the first real encounter stream with saturation, T diverges by one unit, and the divergence compounds through T×z. Their crossing logs and J_F differ, and the conductor's "match all ten trace steps" gate has certified both.

**Minimal fix:**
- Add golden vectors that hit each ambiguity: a saturating M sum, a saturating M − z, a nonzero outer() with a rounding tie, real encounters with T ≠ 0, the 0/1/15-hold and NONE cases already promised in §5.7, the default-z₀ crossing, a through-zero case, a zero-in-window case and an oscillation.
- List T, I and E-before/after as columns.
- State the bounded set explicitly: z, E, M and T bounded; intermediate sums saturating or not; M − z saturating or not.
- Define the classifier's handling of zeros inside the window and of return legs.

#### R3-F12. §5.2: "canonical key order" in CBOR has two published meanings, and field IDs and tags are not given. MINOR, because the doc already marks H4 BLOCKED. PRIOR (RFC 8949 §4.2.1 vs RFC 7049 §3.9 and RFC 8949 §4.2.3).

**The problem:** RFC 8949 core deterministic encoding sorts map keys by the bytewise order of their encodings. The older RFC 7049 canonical form, which RFC 8949 keeps as "length-first", sorts shorter keys first. §5.2 allows signed integers. With integer keys such as 24 (encoded 0x18 0x18) and −1 (encoded 0x20):
- bytewise order puts 24 before −1;
- length-first order puts −1 before 24.

**Failure scenario:** two verifiers following "canonical key order" compute different bytes, and so different base_state_hash values, for the same state. Every Permit is refused by one of them. Field IDs, domain-tag strings and the version are also absent, so nobody can produce the bytes yet.

**Minimal fix:**
- Name RFC 8949 §4.2.1 core deterministic encoding.
- Restrict keys to unsigned 0..23.
- Publish the field-ID table, the exact tag strings and three test vectors.

#### R3-F15. §6 H1 and E1: the target generator and the conventional baseline's update rule are free choices. WOUNDING. DOC.

**What H1 requires:** that T beat "an equally sized conventional state representation" on targets "generated independently of the T reference model".

**What it leaves open:**

- It doesn't say what update rule the conventional state uses.

## The single finding to fix first

**R3-F5.** Rule 1, lineage ground J_F, is v0.6's main new mechanism and the stated repair of our R2-F14. In the reference toy it has no causal path at all, and its deposit has no schema. Until δ_F is defined and the toy Φ reads it, H3 can only fail, and for the wrong reason. The J-empty and J-shuffled controls are meaningless, and the R3-F2 and R3-F8 sequencing questions can't even be tested.

The fix is small: a closed δ_F record, one bounded J term in the toy Φ, and one golden vector with a nonempty J_F.

R3-F1 comes next (n = 4 or drop "malicious"), then R3-F2.

## Blue-sky idea (unscored, excluded from findings)

**Inherited ground with a sunset.** Give every J_F deposit a generation half-life. A descendant inherits it at reduced weight unless the descendant crosses the same way itself, which renews it through its own gate.

This would do three things:
- **Turns H3 into a dose-response test.** Instead of comparing J-present with J-empty, you predict how a deposit's effect should fade with generational distance, which is harder to fake.
- **Limits error propagation.** An uncorrected error fades without anyone having to rewrite history, which eases R3-F7.
- **Matches the paper's frame.** A tradition that each generation re-earns differs from a decree passed down. The renewal rate becomes a measurable property of a family: whether its children keep walking the same crossings.

It doesn't touch the pending grace definition, because the gate still decides each renewal.
